## FE1 #48 integration contract

Import the small bridge into the FE1-owned consultation component:

```tsx
import { SpecialtyDiscoveryLink } from "./specialty-discovery-link";

// In the result area, after the specialty/source/emergency messages:
{result && <SpecialtyDiscoveryLink recommendation={result} />}
```

Required props are `{specialty: string | null, urgent: boolean, followUpRequired: boolean}`. Only explicit `urgent=false`, `followUpRequired=false` and a nonblank specialty produce **View matching doctors**. Emergency, missing safety flags and pending follow-up produce no CTA. FE1 must continue showing the emergency guidance and must remove its old `result.doctors.map(...)` cards/direct booking links from this area. Neither the bridge nor discovery consumes consultation doctor objects or AI-provided IDs.

The URL is `/?specialty=<URLSearchParams-encoded specialty>#book`. Use `discoveryHref(specialty)` from `frontend/src/lib/specialty-handoff.ts` when a URL is needed instead of the component. Known English/Vietnamese aliases canonicalize to backend Vietnamese labels. Unrecognized specialties remain intact and can produce a genuine empty response; they never fall back to General Medicine or a random doctor. No symptoms or conversation text enter the URL.

The existing DoctorBrowser reads the URL itself; its public `query` prop stays unchanged. No `page.tsx` integration changes are needed to read the specialty. FE1 still owns mounting the real consultation in the Patient Portal, replacing the static chat, and keeping its conversation state. In `page.tsx`, replace the static chat-body/form with FE1's live `Consultation` entry; retain their auth/navigation changes. These FE1-owned files were deliberately not edited.

Doctor selection stores `doctor=<catalog UUID>` in the discovery history entry. Both the row and profile CTA open `/doctors/<UUID>/book?specialty=...&doctor=...` using the existing intercepted route. Modal Close/Back uses the existing router back behavior. After refreshing or directly opening the calendar, Close returns to `/?specialty=...&doctor=...#book`. Context is a navigation hint; it does not authorize a booking or override the doctor's catalog profile.

For a signed-out entry, the existing home page shows its guest view. FE1 should preserve `pathname + search + hash` in the Patient login `next` URL when exposing consultation to guests. `safeReturnTo` already accepts root query/hash destinations and the V2 booking route. Real sign-in/session continuity remains FE1 #33 verification work.

## Catalog and V2 behavior

- Uses the existing `doctor-catalog` parser and `fe1Request` transport with `GET /api/doctors?specialty=...`, the existing keyword search and no-store/abort handling. Aliases mirror `backend/app/service.py`: dermatology, cardiology, general medicine/general; accent-insensitive Vietnamese spellings are accepted too.
- Discovery opts into V2 validation of `address`, `certificates`, `rating`, `ratingCount`, alongside UUID/name/specialty/bio/district validation. Existing legacy parser callers keep their previous behavior. DoctorBrowser/Profile no longer reads `clinicName` or `clinicAddress`.
- After validation, matches are checked against the actual catalog response; explicitly inactive and unrelated-specialty rows cannot appear. Backend remains responsible for returning only active doctors (the public V2 Doctor has no required `active` field). No unfiltered fallback request fills an empty recommendation.
- Pending requests show loading instead of another filter's stale results. Empty and error states allow an explicit retry; selected specialties can always be cleared. Demo doctors/times are labeled previews; the existing calendar disables demo booking.
- No doctor, UUID, availability or confirmation is generated by the handoff. Booking POST, JWT authorization, 30-minute slot logic, realtime availability and weekly schedules are unchanged. The only booking-client change is its full-page Close destination.
